# Doc Types And Templates

以下模板不是死格式，而是最低完整度骨架。要依任務調整，但不要拿掉對可執行性很重要的段落。

## README / Quick Start

建議段落：

1. 這是什麼
2. 適合誰
3. 快速開始
4. 安裝與設定
5. 基本使用方式
6. 驗證成功
7. 常見問題或下一步

最低要求：
- 第一屏說清楚產品或 repo 的價值與適用對象
- 在 5 分鐘內能完成一次成功路徑
- 至少有一個驗證成功的方法

## Tutorial

建議段落：

1. 你將學到什麼
2. 前置條件
3. Step 1
4. Step 2
5. Step 3
6. 驗證成果
7. 你剛剛學到了什麼
8. 下一步

最低要求：
- 每一步只引入當下必要資訊
- 每一步都有明確輸出或檢查點
- 失敗時知道要回到哪一步

## How-to Guide

建議段落：

1. 任務目標
2. 前置條件
3. 操作步驟
4. 驗證結果
5. 常見失敗與排除
6. 相關文件

最低要求：
- 用任務導向標題，不要用抽象標題
- 讓熟手可快速跳過背景段落
- 步驟可直接複製執行

## API Usage Guide / Reference

建議段落：

1. Overview
2. Authentication
3. Base URL / Version scope
4. Endpoints or workflows
5. Request parameters
6. Response examples
7. Errors and limits
8. Notes / known issues

最低要求：
- 標出版本範圍與適用環境
- 至少一組成功與失敗範例
- 不清楚的欄位要標成待確認，不要硬補

## Runbook / Troubleshooting

建議段落：

1. 症狀或告警條件
2. 影響範圍
3. 先確認什麼
4. 診斷步驟
5. 修復步驟
6. 驗證服務恢復
7. 回退方案
8. 升級通報條件
9. 事後預防

最低要求：
- 順序必須服務壓力情境下的讀者
- 不要要求值班者先看長篇背景解釋
- 要寫出何時停止自行處理並升級

## Migration Guide

建議段落：

1. 誰需要升級
2. 主要變更摘要
3. Breaking changes
4. 升級前檢查
5. 升級步驟
6. 驗證方式
7. 回退策略
8. 已知限制

最低要求：
- 對不相容變更說清楚影響對象
- 提供升級後驗證與回退資訊
- 不要只貼 changelog

## Docs Audit / Gap Analysis

建議輸出欄位：

1. 受眾
2. 主要任務
3. 目前已有文件
4. 缺少的文件
5. 建議類型
6. 優先順序
7. 缺口風險
8. 建議 owner

最低要求：
- 每份建議文件都要有受眾與任務
- 優先順序必須有理由
- 不要把 audit 假裝成已完成寫作
