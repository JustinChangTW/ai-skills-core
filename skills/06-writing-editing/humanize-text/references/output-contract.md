# 輸出契約

`humanize-text` 的預設輸出是可見化改寫流程加完成稿，不是只貼一版改寫文字。除非使用者明確要求「只要完成稿」，否則必須先列印任務邊界、AI 味盤點、受眾與用途、論點連貫檢測、改寫策略，再交付可用文字與前後指標比較。

## Default output shape

- 不得只輸出完成稿；必須先輸出執行紀錄。
- 預設輸出必須分成三個主要區塊：`前置處理`、`改寫結果`、`前後指標比較`。三者之間必須用 Markdown 分隔線 `---` 隔開，不得只靠小標題連在一起。
- `前置處理` 內依序包含：`TODO`、`任務邊界`、`AI 味盤點`、`受眾與用途`、`論點連貫檢測`、`改寫策略`、`保留邊界`。
- `改寫結果` 只放完成稿與必要短標，不混入修改說明。
- `前後指標比較` 內包含 before/after 指標與自檢結果。
- `TODO` 至少包含確認工具 / skill、讀取必要 references、盤點 AI 味、釐清受眾、指定策略、改寫、前後比較與驗證。
- `AI 味盤點` 必須指出具體問題來源，例如模板式轉場、句型重複、列表殘影、翻譯腔、段落節奏過度平均、受眾缺席或觀點被平均化。
- `受眾與用途` 必須列出使用者提供的資訊或明確假設；若受眾差異會大幅改變內容方向，先追問再改寫。
- `論點連貫檢測` 必須明確覆蓋論點矛盾、同概念換詞重複、段落顆粒度跳躍、階層斷裂與假轉折。沒有發現時，也要標示「未發現明顯矛盾」或「顆粒度穩定」，不得省略。
- `改寫策略` 必須指定 `light polish`、`natural rewrite`、`paragraph reconstruction`、`structural rewrite`、`localized zh-TW` 或 `edit` 其中一個主策略，並說明理由與改寫幅度。
- 一旦受眾與最終目的顯示原開頭、段落順序或主張進場方式會削弱效果，就必須升級為 `structural rewrite`。這種模式允許重寫開頭一到兩段、提前讀者痛點、合併重複段落或重排論點順序；仍不得新增未提供事實或改變作者立場。
- 以自然段落為主，可有短標題，但不得有條列式或有序列表。
- 若原文資訊量較大，優先拆成 2-4 段，不要塞成單一超長段。
- 不主動附「以下是優化後版本」「修改如下」這種模板式前言；流程標題要具體，例如「AI 味盤點」「改寫策略」。
- 一旦使用者指定受眾與預期效果，完成稿的第一個有效段落必須讓讀者知道這段文字跟自己有什麼關係。
- 非純事實內容應保留或強化原文可支持的觀點、判斷或取捨，不輸出平均化、無立場的泛泛整理。
- 非純事實內容的主張、理由、例子、限制與下一步必須形成連貫主張鏈，不得前後矛盾或換詞重複。
- `before/after 指標比較` 必須至少覆蓋列表殘影、重複句型、模板轉場、段落節奏、受眾明確度與事實漂移風險；可量化時給數字，不可量化時用 `低 / 中 / 高` 並附理由。

## Mode-specific output

### rewrite

預設先輸出可見化流程，再輸出改寫後的完成稿。pattern 掃描、受眾推定、論點連貫檢測、策略選擇、保留邊界與 before/after 指標都必須顯示給使用者，不能只在內部完成。rewrite 輸出必須使用 `前置處理`、`改寫結果`、`前後指標比較` 三段式結構，三段之間以 `---` 分隔。

### detect

使用者只問「哪裡像 AI」或要求 review 時，輸出 pattern report。報告要包含問題片段、主要 pattern、原因與修法；同一片語的 pattern stacking 只報一次。此模式可以用短列表，因為使用者要的是診斷而不是完成稿。
一般 rewrite 任務也必須先執行 detect，但 detect-only 模式只有在使用者明確要求只診斷時，才停止於 pattern report。

### edit

使用者提供檔案並要求修改時，先讀檔、做 targeted edits，再回報修改摘要與驗證結果。不得批次改動未指定檔案。
edit 模式同樣必須輸出 AI 味盤點、受眾與用途、改寫策略、before/after 指標與驗證結果。

## Hard constraints

- 不新增原文沒有的事實。
- 不假裝真實個人經驗。
- 不保證通過 AI detector。
- 完成稿不輸出 `-`、`*`、`+`、`1.`、`1)`、`一、`、`二、` 這類列表形式；執行紀錄與 before/after 指標比較可以使用表格或短列表。
- rewrite / edit 任務不得省略三段式分隔；除非使用者明確要求「只要完成稿」，否則 `前置處理`、`改寫結果`、`前後指標比較` 必須同時出現。
- 不用「以下是」「總而言之」「首先／其次／最後」當成預設骨架，除非原文語境確實需要。
- 不留下 placeholder、AI citation markup、錯誤媒介中的 Markdown bleeding 或 AI 工具 UTM 參數。
- 不反覆使用破折號、粗體小標、冒號式短句或不必要分節來製造假結構。
- 不把學術、醫療、法務、財務或技術內容過度口語化。
- 不為了補觀點而新增原文沒有的事實、價值判斷、第一手經驗或反對者。
- 不把純事實、法規、規格、逐字紀錄或資料摘要硬改成評論。
- 不用「此外」「然而」「值得注意」這類 signpost 掩蓋沒有推進的重複敘事。
- 不讓同一概念在同一篇文字中無理由換名，造成讀者以為是不同概念。
- 不因為使用者沒有明講要診斷，就省略 AI 味盤點、受眾釐清、策略指定或前後比較。
- 不把 `structural rewrite` 誤用成自由創作；大幅重排只能服務受眾與目的，且必須保留原文可支持的事實與立場。

## When explanation is requested

若使用者明確要解釋修改重點，先給完成稿，再用短段落說明，不用條列。
若非必要，不要回到「列三點原因」這種機器化說法。

## Self-check before sending

- 是否已用 `前置處理`、`---`、`改寫結果`、`---`、`前後指標比較` 的三段式輸出。
- 是否已列印 TODO、任務邊界、AI 味盤點、受眾與用途、論點連貫檢測、改寫策略。
- 讀一遍，確認段落之間真的有轉承。
- 掃描行首，確認沒有列表標記。
- 對照原文，確認沒有新增觀點或缺漏關鍵名詞。
- 若是繁中，確認讀感不是中國用語直套或英文語序硬譯。
- 確認第一段不是在做沒必要的定義式開場，最後一段也不是硬補總結。
- 確認沒有 pattern stacking 集中在同一句仍未處理。
- 確認沒有過度條列化或破折號濫用；真正需要列表或破折號時，要能說明它服務受眾與媒介。
- 確認正式領域需要的引用、數字、限制與 hedging 沒有被誤刪。
- 確認受眾、預期效果與編排順序一致。
- 確認觀點有原文支持，且沒有把作者立場改掉。
- 確認主張鏈一致、概念命名穩定、段落顆粒度不跳躍。
- 確認是否應該升級為 `structural rewrite`；若原文開頭或段落順序不服務受眾與目的，不能只微調。
- 是否已輸出 before/after 指標比較，並明確標示事實漂移風險。
